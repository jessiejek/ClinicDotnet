## 1. App Overview

### Purpose

A multi-role hospital/clinic web portal that allows patients to browse doctors, book appointments, and manage their health records; staff to manage the daily queue, walk-in registrations, and payments; doctors to view their schedule, conduct consultations, and maintain clinical records; and admins to configure the clinic, manage all users, run reports, and view audit logs.

### Tech Stack (confirmed from source)

| Layer | Technology |
|---|---|
| Framework | Angular 17 (standalone components throughout) |
| UI Library | Ionic Angular 7 (`@ionic/angular/standalone`) |
| Language | TypeScript ~5.4 |
| State | RxJS BehaviorSubjects + Angular Signals (`toSignal`) |
| HTTP | Angular `HttpClient` wrapped by `ApiService` |
| Realtime | Microsoft SignalR (`@microsoft/signalr` v10) |
| Push Notifications | Firebase Messaging v10 (FCM) |

| Social Auth | Google Identity Services (GIS) popup; Facebook JS SDK popup |
| Routing | Angular Router with lazy-loaded standalone components |
| Build | Angular CLI 17 / `@angular-devkit/build-angular` |

| Hosting | Vercel (confirmed from `vercel.json`) |

| Currency | Philippine Peso (PHP) — `PesoPipe` uses `en-PH` locale |
| Timezone | Asia/Manila used for all date calculations |

### Auth Mechanism

**Login flow (email/password):**

1. `POST /auth/login` with `{ email, password }`.
2. Response: `AuthSessionDto` containing `accessToken`, `refreshToken`, `user`.
3. `TokenService.setTokens()` persists both tokens to `localStorage` under keys `clinic.auth.access-token` and `clinic.auth.refresh-token`.
4. `AuthStateService.setUser()` stores `AuthUser` in memory (`BehaviorSubject`) and calls `AuthService.persistUser()` which writes to `localStorage` under `clinic.auth.user`.
5. `AuthService.navigateByRole()` redirects based on the resolved role.

**App initialisation (reload/refresh):**

On bootstrap, `APP_INITIALIZER` (`initializeAuthSession` in `app.config.ts`) reads tokens from `localStorage`. If tokens exist, it calls `GET /auth/me` to rehydrate the authenticated user into `AuthStateService`. On failure it calls `authState.logout()`.

**Social login (Google / Facebook):**

- Google: loads GIS script lazily, calls `requestAccessToken()`, then `POST /auth/google` with `{ provider, idToken, accessToken }`.
- Facebook: loads FB SDK lazily, calls `FB.login()`, then `POST /auth/facebook` with `{ accessToken, userId }`.
- Both paths follow the same store-tokens → set-user → navigate-by-role sequence.

**Token refresh:**

The `authInterceptor` attaches `Authorization: Bearer <accessToken>` to all non-public requests. On a `401` response it calls `POST /auth/refresh-token` with `{ refreshToken }`, updates tokens, and retries the original request once (guarded by `AUTH_RETRY_ATTEMPTED` context token). On refresh failure it clears the session and redirects to `/auth/login`.

**Logout:**

`AuthStateService.logout()` clears the in-memory `BehaviorSubject`, calls `AuthService.clearSession()` which removes all three `localStorage` keys, and clears the error/loading subjects.

**Auth callback page (`/auth/callback`):**

Reads `access_token` and `refresh_token` from the URL hash fragment (OAuth redirect flow). Stores tokens and calls `GET /auth/me` to hydrate the user, then navigates by role. This is the entry point for redirect-based OAuth flows (distinct from the popup-based flows used by the main login page).

### Role Detection

Role is determined in `AuthService.resolveRole()`:

1. First attempts `normalizeRole()` on the `role` string returned by the backend in `AuthUserDto.role`.
2. If that fails, attempts to decode the JWT `accessToken` and reads the role from any of: `role`, `Role`, `roles`, or the Microsoft claim URI `http://schemas.microsoft.com/ws/2008/06/identity/claims/role`.
3. If neither succeeds, throws `Unable to determine authenticated user role.`

Valid roles: `'Admin' | 'Staff' | 'Doctor' | 'Patient'` (case-insensitive match, then normalised to title-case).

After detection, the role is stored in `AuthUser.role` and exposed via `AuthStateService.userRole$` (Observable) and `AuthStateService.userRole` (Signal).

## 2. Role: Doctor

### Entry Point / Login Flow

1. Doctor logs in at `/auth/login`.
2. `navigateByRole()` redirects to `/doctor/dashboard`.
3. `firstLoginGuard` intercepts if `isFirstLogin === true` and redirects to `/auth/set-password` instead.
4. The `PortalLayoutComponent` (shared shell) is used; `RealtimeInitService` is injected, activating SignalR and push notification subscriptions.

### Pages and Routes

All routes are protected by `authGuard` + `roleGuard` (roles: `['Doctor']`).

#### `/doctor/dashboard` — `DoctorDashboardPage`

**Data displayed:**
- Doctor's own profile (name, specialization, avatar, `profilePhotoUrl`).
- Today's availability status badge (Available / RunningLate / UnavailableToday).
- KPI cards: Booked Today, Waiting, Checked In, Completed.
- "Up Next" patient banner (next queued booking with queue number, time, service).
- Today's full queue list (sorted by queue number) with status badges.
- Weekly schedule summary (working days and hours).

**API calls:**
- `GET /doctors/me` — own doctor profile.
- `GET /bookings/doctor/today` — today's booking list.
- `GET /bookings/doctor/today-summary` — aggregate stats (`DoctorTodaySummary`).
- `GET /doctors/{id}/schedule` — working day schedule.
- `GET /doctors/{id}/day-status` — today's availability status.

**Actions:**
- Click queue item → navigates to `/doctor/appointments/{id}`.
- Click "Start Consult" (Up Next banner) → navigates to `/doctor/consultation/{bookingId}`.
- Click "View Chart" → navigates to `/doctor/patients/{patientId}`.
- Change availability status (Available / RunningLate / UnavailableToday): `POST /doctors/{id}/day-status` with `{ date, status, runningLateMinutes? }`.
- Realtime: listens to `ClinicDashboardRealtimeService` events (`BookingCreated`, `PatientCheckedIn`, `DoctorCompletedConsultation`) to refresh the queue live.

#### `/doctor/appointments` — `DoctorAppointmentsPage`

**Data displayed:**
- Stat bar: Booked, In Clinic, Waiting, Completed, No Show, Cancelled for today.
- Filterable list of today's appointments (filter: all / Confirmed / CheckedIn / Completed / NoShow / Cancelled).
- Each row: patient name, queue number, time, service(s), status badge.

**API calls:**
- `GET /bookings/doctor/today` — today's booking list.
- `GET /bookings/doctor/today-summary` — stats summary.

**Actions:**
- Filter tabs to switch view.
- Click row → navigate to `/doctor/appointments/{id}`.
- Mark complete inline (from this page): `PATCH /bookings/{bookingId}/doctor-complete` with `DoctorCompleteBookingRequest`.
- Waive professional fee inline: `PATCH /payments/{bookingId}/waive` with `{ reason }`.
- Realtime refresh on `ClinicDashboardRealtimeService` events.

#### `/doctor/appointments/:id` — `DoctorAppointmentDetailPage`

**Data displayed:**
- Full booking detail (patient name, doctor, service, date/time, status, payment, queue number).

**API calls:**
- `GET /bookings/{bookingId}` — full booking record.

**Actions:**
- Navigate to consultation form: link to `/doctor/consultation/{bookingId}`.

#### `/doctor/consultation/:bookingId` — `DoctorConsultationPage`

This is the most complex page in the application (~2900 lines). It is the full clinical encounter form.

**Data displayed:**
- Patient info panel: demographics, contact, allergies.

- `GET /medical-records/consultations?patientId={id}` — consultation history.
- `GET /medical-records/prescriptions?patientId={id}` — prescription history.
- `GET /medical-records/allergies?patientId={id}` — allergies.
- `GET /medical-records/lab-orders?patientId={id}` — lab order history.
- `GET /medical-records/lab-results?patientId={id}` — lab results.
- `GET /medical-records/vaccinations?patientId={id}` — vaccination history.
- `GET /medical-records/follow-ups?patientId={id}` — follow-up history.

- `PUT /bookings/{bookingId}/consultation-record` — auto-save/draft of consultation record.
- `PATCH /bookings/{bookingId}/doctor-complete` — finalise consultation (triggers status transition to Completed).
- `PATCH /payments/{bookingId}/waive` — waive professional fee.

- `POST /consultation-requests/request-attending-physician` — [NEEDS CLARIFICATION: beta/partial feature, endpoint may not be live].

**Actions:**

- Auto-save (PUT consultation record) on field change.

### Key User Flows — Doctor

**Flow: Doctor starts a consultation**
1. Doctor opens `/doctor/dashboard` → sees "Up Next" patient banner.
2. Clicks "Start Consult" → navigates to `/doctor/consultation/{bookingId}`.
3. Consultation page loads all patient history via parallel `forkJoin` API calls.
4. Doctor fills SOAP notes, vital signs, diagnoses.
5. Adds prescriptions via prescription builder component.
6. Adds lab requests via lab request form component.
7. Sets follow-up date/reason.
8. Clicks "Complete Consultation" → `PATCH /bookings/{bookingId}/doctor-complete` with full payload.
9. Booking status transitions to `Completed`. Patient moves to payment queue for Staff.

**Flow: Doctor sets availability status**
1. On Dashboard, doctor selects status from availability panel.
2. `POST /doctors/{id}/day-status` with `{ date, status }`.
3. Other portals receive the `DoctorScheduleUpdated` SignalR event.

## 3. Role: Patient

### Entry Point / Login Flow

1. Patient registers at `/auth/register` (self-registration) or is created by Staff/Admin and given a portal account.
2. After login, `navigateByRole()` → `/patient/dashboard`.
3. `firstLoginGuard` → `/auth/set-password` if `isFirstLogin`.
4. New patients may also be redirected to `/auth/privacy-consent` (route guarded for Patient role) to consent to the privacy policy.
5. Patient portal uses `PatientLayoutComponent` (distinct from `PortalLayoutComponent`), which also reuses the `SidebarComponent` and `TopbarComponent` from admin.

### Key User Flows — Patient

**Flow: Patient books an appointment (public wizard)**
1. Patient visits `/public/booking` (no auth required) or clicks "Book Now" from doctor profile.
2. **Step 1 (Doctor & Service):** Selects a doctor from the list (`GET /doctors`), then selects one or more services (`GET /doctors/{id}/services`).
3. **Step 2 (Date):** Picks a date from a calendar (days filtered against doctor's working schedule).
4. **Step 3 (Slot):** Selects a time slot (`GET /doctors/{id}/available-slots?date={date}`).
5. **Step 4 (Auth Check):** If not logged in, prompted to log in or continue as guest.
6. **Step 5 (Payment/Proof):**
   - If `PayAtClinic` mode: confirms booking directly.
   - If `Online` mode: submits reference number or screenshot proof.
7. `POST /bookings` with `{ doctorId, serviceIds, appointmentDate, slotStartTime, slotEndTime, notes? }`.
8. On success:
   - Logged-in patient → redirected to `/patient/bookings/{bookingId}`.
   - Guest → redirected to `/public/booking-confirmation/{bookingId}`.

**Flow: Patient cancels a booking**
1. Opens `/patient/bookings`.
2. Clicks booking card → `/patient/bookings/{id}`.
3. Clicks "Cancel Booking" → confirm modal appears.
4. Confirms → `PATCH /bookings/{id}/cancel` with reason "Cancelled by patient."
5. Status updates to `Cancelled` on the page.

### Logout

Any portal's sidebar includes a logout button. Clicking it calls `AuthStateService.logout()`:
1. Clears user BehaviorSubject.
2. Clears error and loading subjects.
3. Calls `AuthService.clearSession()` → removes `clinic.auth.access-token`, `clinic.auth.refresh-token`, `clinic.auth.user` from `localStorage`.
4. [NEEDS CLARIFICATION: No `POST /auth/logout` API call is made from the frontend — server-side token invalidation is not confirmed.]
5. Angular Router navigates to `/auth/login` (implied; not explicitly traced in logout handler but `navigateByRole` defaults there on failed auth).

### Notifications

- `PushNotificationService` connects to SignalR and Firebase FCM on login.
- `NotificationService` merges live SignalR notifications into a `BehaviorSubject<Notification[]>`.
- `NotificationPanelComponent` (in topbar) displays unread count badge and dropdown list.
- Mark one as read: `PUT /notifications/{id}/read`.
- Mark all as read: `PUT /notifications/read-all`.
- On logout, `NotificationService` clears the notifications array (triggered by `currentUser$` emitting `null`).

### Password Management

- **Forgot password:** `POST /auth/forgot-password` with `{ email }` → shows success message.
- **Reset password:** `/auth/reset-password` page → `POST /auth/reset-password` with `{ token, newPassword }`.
- **Set password (first login):** `/auth/set-password` (guarded by `authGuard`) → `POST /auth/set-password` with `{ newPassword }` → calls `GET /auth/me` to re-fetch updated user → navigates by role.
- **Change password (from profile):** `POST /auth/change-password` with `{ currentPassword, newPassword }` (Doctor, Patient, Staff profiles all use this).

### Profile Photo Upload

- Staff: `POST /auth/avatar` (FormData) → returns `{ avatarUrl }`.
- Doctor: `POST /doctors/{id}/photo` (FormData) → returns `{ profilePhotoUrl }`.
- Admin-managed doctor photo: same endpoint via `DoctorFormPage`.

### SignalR Realtime Events

`ClinicDashboardRealtimeService` maintains a persistent SignalR hub connection to `{signalrHubUrl}` authenticated via Bearer token. It emits a shared `events$: Observable<ClinicDashboardEvent>` stream.

Events subscribed to:

| Event Name | Triggering Action |
|---|---|
| `BookingCreated` | New booking placed |
| `BookingCancelled` | Booking cancelled |
| `PatientCheckedIn` | Staff checks in a patient |
| `PatientCheckInUndone` | Staff reverts check-in |
| `DoctorCompletedConsultation` | Doctor marks consultation complete |
| `PaymentCompleted` | Staff confirms payment |
| `PaymentWaived` | Staff/Admin waives payment |
| `DoctorScheduleUpdated` | Admin/Doctor updates schedule |
| `DoctorServicesUpdated` | Services linked to doctor changed |
| `PatientProfileUpdated` | Patient profile changed |

These events are consumed by Dashboard pages (Staff, Doctor, Admin) to refresh displayed data without manual page reload.

## 13. Security & Permissions

### Route Guards

| Guard | File | Logic |
|---|---|---|
| `authGuard` | `core/guards/auth.guard.ts` | Reads `AuthStateService.isAuthenticated$`; if false, redirects to `/auth/login` |
| `roleGuard` | `core/guards/role.guard.ts` | Reads `AuthStateService.userRole$`; compares against `route.data.roles`; if no match, redirects to `/auth/login` |
| `firstLoginGuard` | `core/guards/first-login.guard.ts` | Reads `AuthStateService.currentUser$`; if `user.isFirstLogin === true`, redirects to `/auth/set-password` |

**Guard combinations by route:**

| Route prefix | Guards applied |
|---|---|
| `/admin/*` | `authGuard`, `roleGuard` (roles: `['Admin']`), `firstLoginGuard` |
| `/staff/*` | `authGuard`, `roleGuard` (roles: `['Staff']`) |
| `/doctor/*` | `authGuard`, `roleGuard` (roles: `['Doctor']`) |
| `/patient/*` | `authGuard`, `roleGuard` (roles: `['Patient']`) |
| `/auth/set-password` | `authGuard` only |
| `/auth/privacy-consent` | `authGuard`, `roleGuard` (roles: `['Patient']`) |
| `/public/*` | None |
| `/dev/*` | None |

Note: Staff portal does **not** apply `firstLoginGuard` at the route level (unlike Admin). Doctor portal does not apply `firstLoginGuard` at the child route level (only on the parent layout route).

### Token Storage

| Token | Key | Storage |
|---|---|---|
| Access token | `clinic.auth.access-token` | `localStorage` |
| Refresh token | `clinic.auth.refresh-token` | `localStorage` |
| User object | `clinic.auth.user` | `localStorage` |

Tokens are also held in-memory in `TokenService` private fields for fast synchronous access without repeated `localStorage` reads.

**Security note:** Storing JWT in `localStorage` is susceptible to XSS. There is no `httpOnly` cookie strategy.

### Token Refresh Strategy

- Handled by `authInterceptor` (functional interceptor, registered via `provideHttpClient(withInterceptors([authInterceptor]))`).
- On 401 response for non-public, non-already-retried requests: `POST /auth/refresh-token` with `{ refreshToken }`.
- On success: stores new tokens, retries original request exactly once (via `AUTH_RETRY_ATTEMPTED` context token to prevent infinite loops).
- On failure: clears session, navigates to login.

### Session Expiry

- No client-side JWT expiry checks (no `exp` claim parsing for proactive refresh).
- Expiry is handled reactively: any protected API call that returns 401 triggers the refresh flow.
- If refresh also fails, user is logged out.

### Public Endpoints (no auth header attached)

Defined in `authInterceptor`'s `isPublicAuthEndpoint()`:
- `/auth/login`
- `/auth/register`
- `/auth/register-patient`
- `/auth/google`
- `/auth/refresh`
- `/auth/logout`

## 14. Error Handling Strategy

### HTTP Error Handling

**Global interceptor:** `authInterceptor` handles only `401` errors for token refresh. All other errors are passed through via `throwError(() => error)`.

**Per-service / per-page:** Most API calls use per-call `catchError()` operators. The pattern:

```typescript
this.apiService.get<T>('endpoint').pipe(
  catchError((error: unknown) => {
    // Either return of([]) / of(null) as safe fallback
    // Or throwError(() => new Error(extractApiErrorMessage(error, 'Fallback message')))
  }),
  finalize(() => this.isLoading = false)
).subscribe({ error: () => undefined });
```

**`extractApiErrorMessage()` function** (duplicated in `BookingService` and `LoginPage`): Extracts user-readable message from `HttpErrorResponse` by checking `error.message`, then `error.errors` (validation errors dict), then `err.message`, then returns the provided fallback string.

**`ApiService.handleError()`:** Logs to `console.error` and re-throws. No global interception.

### Error Display to User

| Mechanism | Component / Context | Usage |
|---|---|---|
| `ToastController` | All portals, via `BaseComponent.showToast()` or direct injection | Action feedback (success green, error danger/red), 1800ms duration, position: top |
| `app-banner` | Login page, Patient dashboard, Set-Password page | Inline persistent error (can be dismissed) |
| `app-empty-state` | All pages when lists are empty | Zero-data state with optional retry button |
| Inline error div | Individual forms | Simple `*ngIf="error"` text blocks |
| `app-skeleton` + retry button | Pages that fail to load | Shown during loading; error state replaces skeleton with retry |

**Toast configuration:** 1800ms duration by default (`BaseComponent.showToast()`); some pages use 3000ms.

### Global Error Handling

There is **no `ErrorHandler` override** and no global `catchError` at the `HttpClient` level beyond the auth interceptor. Error handling is per-component/per-service.

### Service Structure

Services are `@Injectable({ providedIn: 'root' })`. API calls are made through the central `ApiService` (never direct `HttpClient` injection). Services use `inject()` (not constructor injection) consistently.

### Routing

- Top-level `app.routes.ts` with `loadChildren` for portal sub-modules.
- Portal routes are constants (`ADMIN_ROUTES`, `DOCTOR_ROUTES`, etc.) in each portal's `*.routes.ts`.
- Navigation items (`ADMIN_NAV_ITEMS`, etc.) are exported constants from routes files and passed as `data` props to the layout component.
- Route parameters: always `id` for resource IDs (e.g. `:id`, `:bookingId`).

### Observable / Promise Patterns

- **RxJS Observables** are the primary async pattern for HTTP calls and state streams.
- `async/await` with `firstValueFrom()` is used for imperative sequences (form submissions, multi-step operations in wizard components).
- `takeUntilDestroyed(this.destroyRef)` (preferred) or `takeUntil(this.ngUnsubscribe)` (via `BaseComponent`) for subscription cleanup.
- `forkJoin()` for parallel requests (dashboard pages, consultation page load).
- `combineLatest()` for streams that depend on multiple sources.
- `switchMap()` for dependent sequential requests.

### Form Handling

**Reactive Forms only.** No template-driven forms. All forms use `FormBuilder.nonNullable.group()` or `FormBuilder.group()`. Validator composition uses `Validators` from `@angular/forms` plus custom `passwordStrengthValidator`. Form group validators used for cross-field validation (password match).

## 17. Known Gaps, Bugs & Incomplete Features

### Confirmed Incomplete Features

**1. Patient Vaccinations — Not functional**
`PatientVaccinationsService` explicitly stubs all methods:
> "not available yet — patient_vaccinations table not deployed"

`getPatientVaccinations()` returns `of([])`. Create/update/delete throw `Error`. The `/patient/vaccinations` page renders but is always empty with no user-visible error message.

**2. Rescheduling — Not implemented**
`BookingService.rescheduleBooking()` is marked `@deprecated`:
> "rescheduleBooking() is deprecated (no API call yet)."

The method logs a warning and does nothing. There is no reschedule UI visible in any portal.

**3. Staff firstLoginGuard — Missing**
`/staff/*` routes apply `authGuard` + `roleGuard` but **not** `firstLoginGuard` at the parent route level (unlike `/admin/*`). Staff users with `isFirstLogin: true` can access the staff portal without being forced to set a password first.

**4. Doctor portal firstLoginGuard — Partially applied**
The doctor portal `PortalLayoutComponent` route has `canActivate: [authGuard, roleGuard]` but not `firstLoginGuard` in `doctor.routes.ts`. The guard is applied only at the root app routes (`app.routes.ts`), not at the child layout route level.

**5. Admin Settings Load Endpoint — Unclear**
The `ClinicSettingsService` initialises with hardcoded defaults. No `GET /settings` call is confirmed to populate it on app startup or on settings page load. The portal layout component (`PortalLayoutComponent`) may load settings but the exact flow is not fully confirmed. The Settings page reads from `ClinicSettingsService.load()` (sync snapshot). [NEEDS CLARIFICATION: When and where `GET /settings` is called to hydrate `ClinicSettingsService`.]

**6. Bulk Booking Actions — UI without backend**
Admin Bookings page has a bulk-select checkbox column but no confirmed `POST /bookings/bulk-*` or similar endpoint call in the page's source.

**7. Attending Physician Request — Beta/Unclear**
`POST /consultation-requests/request-attending-physician` exists in the Doctor Consultation page. This feature is not documented and may be a partial or planned feature. [NEEDS CLARIFICATION: Intended UX and backend support.]

**8. Doctor Profile Photo Upload Endpoint Inconsistency**
`DoctorFormPage` (admin) uses `POST /doctors/{id}/photo`. `DoctorProfilePage` (doctor self-edit) uses `PUT /doctors/me` but `postFormData` is not clearly confirmed for the self-edit photo upload — only the admin form clearly calls `postFormData`. [NEEDS CLARIFICATION: Whether `/doctors/me` supports photo upload directly or uses a separate endpoint.]

**9. Two Firebase VAPID Keys**
`environment.ts` contains both `firebaseVapidKey` and `vapidKey` with different values. [NEEDS CLARIFICATION: Which one is active? `PushNotificationService` should use one of them to register the service worker token.]

**10. Auth Callback Page — Legacy/OAuth Redirect**
`/auth/callback` reads tokens from URL hash fragments, suggesting it supports OAuth redirect flows. However, the login page uses popup flows only. [NEEDS CLARIFICATION: When is `/auth/callback` actually used? Is it for a future mobile/native OAuth redirect or a legacy flow?]

**11. `GET /auth/logout` — Not called from frontend**
The `isPublicAuthEndpoint` whitelist includes `/auth/logout`, but no component or service in the frontend calls this endpoint on logout. Server-side token revocation on logout is not guaranteed.

**12. `PatientDocumentsService.getDownloadUrl()` — Unused in UI**
`PatientDocumentsService` exposes a `getDownloadUrl()` helper, but the actual download in `PatientMediaPanelComponent` uses `ApiService.getBlob()` directly. The service method appears unused.

**13. `ClinicalRole` — Not populated**
`AuthUser.clinicalRole` field exists in the model (`physician | nurse | medical_assistant | admin | receptionist`) but is never set from any confirmed API response. The `toAuthUser()` method does not map it from `AuthUserDto`.

**14. `BaseComponent.ngUnsubscribe` vs `takeUntilDestroyed`**
Two different subscription cleanup patterns coexist: `takeUntilDestroyed(this.destroyRef)` (newer, idiomatic Angular 17) and `takeUntil(this.ngUnsubscribe)` from `BaseComponent` (older pattern). Some admin pages still extend `BaseComponent` while most new pages use `DestroyRef`.

Frontend logout clears tokens locally but does not call the server, meaning refresh tokens remain valid on the server until they naturally expire. [NEEDS CLARIFICATION: Backend TTL for refresh tokens.]
